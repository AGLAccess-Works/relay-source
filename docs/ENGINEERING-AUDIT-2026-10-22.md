# Relay engineering audit — 22 October 2026

This review examines Relay for engineering and accessibility assessment. It examines the current source, Windows integrations, input ownership, release dependencies, rendered interface and low vision access. It does not certify that every Windows application, controller, screen reader or future Windows release will work.

## Assessment

**No exploit mechanism or DLL injection was found in the reviewed source.** Relay uses documented controller, accessibility and desktop input APIs at the current user's privilege level. Its manifest requests `asInvoker` with `uiAccess="false"`; the installer requests the lowest privilege level. There is no custom driver, process-memory modification, remote-thread creation, global keyboard-hook installation or security-boundary bypass in the inspected code. A search for the relevant mechanisms and older controller middleware found no matches in 108 code/build files. This is source-review evidence, not a proof that all vulnerabilities are absent.

Relay **does generate synthetic mouse and keyboard input using SendInput**. Microsoft calls this input injection in its API documentation. It is an ordinary supported interface and is different from loading a DLL into another process. Windows restricts it through User Interface Privilege Isolation. Relay reports blocked delivery and retains cleanup ownership; it does not elevate to circumvent the restriction. Administrator windows, UAC and the secure desktop remain access limitations. See [Microsoft's SendInput contract](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput).

The low vision foundation is substantial: independent text size, contrast palettes, visible focus, ordinary text alternatives to controller drawings, simplified stable input presentation, keyboard/controller navigation and optional Windows reading tools. The audit nevertheless found real gaps and corrected them. Passing automated checks establishes the measured behavior below; acceptance with low vision users and real assistive technology is still required.

## Findings and changes

| Finding | Impact | Resolution |
| --- | --- | --- |
| Relay's text-size preference did not read Windows' separate text-size preference | A person who already enlarged Windows text could encounter smaller text on first opening Relay | Relay now reads the documented `UISettings.TextScaleFactor`, listens for changes and uses the larger of Windows text size and the saved Relay preference. Supported Windows factors through 225% are covered. No Windows settings or saved profile values are changed. |
| Sidebar labels could break in the middle of a word at large text sizes | Page names became harder to recognise even though their geometric bounds passed | The rail reserves the measured label width and scrollbar space. Narrow windows with enlarged text omit decorative icons to leave more room for page names. New verification rejects broken navigation words. |
| Motion learning had a fixed 280-pixel minimum width | The choice could exceed the available page width with large Windows text | The choice now stretches within its parent and retains a 44-pixel minimum target. |
| Adaptive ports artwork was enlarged beyond its available pixels at this display's DPI | The drawing became blurred | Bitmap artwork now gives way to the existing vector controls when its pixels cannot cover the rendered resolution. Targets retain their size and mappings. A DPI change refreshes the drawing and controls. |
| Native imports did not explicitly restrict the library search directory | Loading behavior was less constrained than necessary for system-only libraries | Assembly-level `DefaultDllImportSearchPaths(System32)` now applies to Relay's native imports, including verification imports. This is defense in depth; no active DLL substitution was demonstrated. |
| DWM dark-frame attribute 20 was called on Windows 10, although its documented availability starts with Windows 11 | The older Windows path relied on an unsupported cosmetic request | The call is now gated to Windows 11 and takes the initial Relay theme into account. |
| The local SDK's default self-contained runtime was 10.0.10 | Rebuilding without an explicit patch could embed an older runtime | The release script now selects .NET 10.0.13 by default, including the app host and desktop runtime. The Windows SDK reference retains its independent version. The isolated audit candidate uses both runtime frameworks at 10.0.13. |

The documented text-size API is described in [UISettings.TextScaleFactorChanged](https://learn.microsoft.com/en-us/uwp/api/windows.ui.viewmanagement.uisettings.textscalefactorchanged). Microsoft also requires readable default text and support for system text settings in its [accessible text guidance](https://learn.microsoft.com/en-us/windows/apps/design/accessibility/accessible-text-requirements). The library-loading control is a [documented .NET attribute](https://learn.microsoft.com/en-us/dotnet/api/system.runtime.interopservices.defaultdllimportsearchpathsattribute). The DWM attribute's Windows 11 boundary is documented in [DWMWINDOWATTRIBUTE](https://learn.microsoft.com/en-us/windows/win32/api/dwmapi/ne-dwmapi-dwmwindowattribute).

## Windows dependencies and maintenance outlook

| Integration | Current implementation | Long-term assessment |
| --- | --- | --- |
| Controller input and vibration | Windows' `xinput1_4.dll` | An inbox system component, not a downloaded XInput 1.3 DLL or controller emulation driver. Microsoft recommends GameInput for new code. Keep a GameInput migration on the roadmap, with hardware parity tests before changing the backend. |
| Device model metadata | `Windows.Gaming.Input` | Used as optional identification information. Missing or ambiguous metadata does not establish a physical accessory connection. Model discovery failure has a fallback. This can be reviewed alongside a GameInput migration. |
| Mouse and keyboard output | `user32.dll` / SendInput | Documented desktop input synthesis with Windows security limits. No supported API can guarantee delivery to every target application. |
| Target assistance and scroll feedback | Windows UI Automation | Reads accessible controls on background threads. Password controls are excluded and stale results are discarded. Unresponsive third-party providers remain an integration risk; the time budgets cannot interrupt a provider call already blocked in COM. |
| Relay's keyboard and target overlay | Ordinary WPF windows with documented window styles | The no-activate and click-through styles apply to Relay's own windows. `SetWindowLongPtr` here is not foreign-process code injection. |
| Window message handling | WPF `HwndSource.AddHook` on Relay windows | Handles Relay's own messages and pause hotkey. It is not a system-wide hook or DLL hook. |
| Windows accessibility tools | System-directory Narrator/Magnifier launches, documented shortcuts and Settings URIs | No private Magnifier hooks or screen-reader DLL injection. Shortcut configuration, Windows version, language and permissions can affect availability. |
| Application framework | .NET 10 WPF, WinForms tray integration | An actively serviced runtime family. Plan a major-version upgrade before .NET 10 support ends on 14 November 2028 and refresh the embedded runtime with servicing releases. |

[Microsoft's XInput version documentation](https://learn.microsoft.com/en-us/windows/win32/xinput/xinput-versions) identifies 1.4 as a system component. Its [GameInput introduction](https://learn.microsoft.com/en-us/gaming/gdk/docs/features/common/input/overviews/input-overview) recommends GameInput for new code and describes XInput among the older APIs it supersedes. These sources do not provide an XInput removal date. Calling Relay permanently future-proof would therefore be unjustified.

The checked [Microsoft support policy](https://dotnet.microsoft.com/en-us/platform/support/policy/dotnet-core) lists 10.0.13 as the current .NET 10 patch on 22 October 2026. A self-contained app carries its own runtime; updating the PC's shared runtime does not update that embedded copy. Continue maintaining the release script's patch version and use a serviced development SDK.

The original C++ project remains in `XboxControllerMouse/` and `XboxControllerMouse.Legacy.sln`. The maintained solution and release script build `src/ControllerMouse.App`; the C++ executable is not part of that publish. Clearly identify the legacy directory when sharing source, and exclude old binaries, local tools, settings, logs and accumulated test artifacts from a future source package.

## Input, privacy and recovery review

The input code tracks Relay-owned keys and mouse buttons. Tests cover incomplete native delivery, retrying releases, external modifiers, disconnecting during a drag, pause/resume, neutral rearming, profile changes, stale queued navigation and suspension. Recording accessories or configuring a shortcut does not grant arbitrary process execution through an imported profile. Profile imports use structured JSON, constrained names, size limits and binding validation.

Process starts in the production path resolve to known Windows tools, fixed Settings URIs or Relay's local data directory. The startup registry value is per-user and opt-in. No application network client, telemetry uploader, global keylogger or automatic software downloader was found in the production source. The build-tool bootstrap does download a known Inno Setup installer and checks its publisher signature. Windows voice typing can use Windows' own speech service; this is separate from Relay's application networking.

Local files include settings, profiles, optional movement/target learning and diagnostics. Target memory records control categories, not the text of visited controls. Diagnostics deliberately omit custom key values. Local logs and user-created profile names can still contain personal information and should not be included automatically in a code handoff.

## Verification and evidence

Evidence is under `artifacts/audit-2026-10-22/`, with the final executable in `reviewed-candidate/` and the final full interface run in `reviewed-acceptance/`. This directory is local and ignored by Git. The executable identity and final results are recorded separately in `final-summary.json`.

- **358 core tests passed.** They cover controller processing, output ownership, profile validation and recovery, keyboard behavior and visual preferences, including the new system-only native import policy and Windows text-size resolution.
- The complete WPF suite covers **220 page/window/Relay-text-size combinations**, four window sizes down to 640×480, **3,480 action target checks**, setup and owned dialogs, profile exploration/activation, switch navigation, pause recovery, keyboard presentation, UI Automation and all seven display schemes.
- Added Windows-text-size verification covers **66 page/window cases** and **948 targets in the full suite** (906 in the standalone default state), at 125%, 150% and 225%, plus preservation of a saved 180% preference and keyboard focus when the system factor returns to normal. These factors are injected into the production layout path; the tests do not change Windows' own settings or establish delivery of a real OS event.
- Palette verification covers **489 combinations**, including custom highlights, rendered action text, selection and focus contrast. Windows contrast checks preserve system colors; they cannot certify every custom Windows palette.
- Microsoft Defender reported **no threats** in the audit candidate and in a staged copy of the 136 source/build/asset files. Scans used custom, non-remediating mode. A clean antivirus result does not establish code correctness or exclude unknown vulnerabilities.
- NuGet's online vulnerability check, including transitive packages, completed without reporting vulnerable packages. Initial restricted-network attempts failed and are retained separately. The successful report does not replace servicing the bundled .NET runtime.
- Rendered screenshots were inspected for the main controller view, ports layout, enlarged text and navigation. The first computer-use capture failed to obtain foreground process metadata; it is not counted as a successful manual interaction test.
- The corrected **native typing fixture passed** on the final reviewed candidate. The real controller processor delivered a native mouse click to Relay's keyboard, which delivered actual key input to its owned editor. Plain text, Shift, Ctrl+A and Backspace worked; editor focus was retained and no inputs remained held. This uses synthetic controller states and does not establish physical controller use.

Early failed runs are retained. The setup-focus loss did not recur on an uninterrupted repeat. The artwork-resolution failure was reproduced and corrected. The new text-size fixture exposed clipped motion-learning controls and broken sidebar words, which were corrected. Another failure came from a ScrollPattern test assuming the page was already at its top; that probe now establishes its starting position, and the text-size fixture restores page scroll positions.

The combined native-input attempts did not establish an end-to-end pass. One stopped before sending input because Windows refused foreground activation; another could not position the pointer. A desktop-access retry stopped its guard when the foreground or pointer no longer belonged to Relay's window. The code preserved the guard and cleanup; the underlying interruption was not attributed conclusively. The first independent native-typing attempt also exposed a fixture construction defect: the same editor was attached to two visual parents. The fixture now attaches it to one parent and passed on a separate native-typing run. Native pointer acceptance remains open; fake-boundary tests and the complete WPF suite do not close it.

## Acceptance still needed before a public release

1. **Low vision user journeys:** independently install/open Relay, understand the current status, choose reading help, find Magnifier zoom, inspect an assignment, change it, pause, resume and recover after a disconnect. Record completion, effort, wrong actions, visual search and fatigue. Include users who use magnification without a screen reader and users who combine the two.
2. **Real assistive technology:** listen with Narrator and NVDA; check focus order, slider values, dialog cancellation, hover reading and repeated announcements. Verify Magnifier tracking and zoom while navigating Relay. Test braille with the actual display when supported. UIA names and synthetic events do not establish understandable speech.
3. **Real display settings:** change Windows text size while Relay, setup and its keyboard are open; confirm reflow and preserved focus. Repeat with Windows contrast themes and mixed-DPI monitors. The automated injected-factor test is only part of this acceptance.
4. **Actual controllers and accessories:** USB, Bluetooth and wireless; standard and Adaptive controllers; four switches and pedals; held controls, drag/disconnect, sleep/resume, and multiple connected controllers. The current automation uses synthetic controller states, even when exercising real WPF controls.
5. **Windows feature availability:** verify every exposed Settings link on supported released builds. In particular, the Screen tint URI is absent from the checked [official Settings URI listing](https://learn.microsoft.com/en-us/windows/apps/develop/launch/launch-settings); its current Windows 11 minimum-build gate does not prove availability. Treat this optional link as unverified until exercised on a build that provides the feature.
6. **Distribution:** code signing and clean-machine install/upgrade/uninstall with the exact final package. The audit executable is unsigned. Existing beta packages were not replaced, installed or uploaded in this review.

CVI simplification is an optional presentation choice, not a claim that every person with CVI benefits from the same design. Low vision, blindness and physical access needs should remain independent preferences. Preserve large text and focus support across profiles, avoid color-only feedback, and keep the ordinary Control view focused on the next usable action. These principles are already reflected in much of Relay; the remaining acceptance must establish their usefulness with people.

**Recommendation:** use the source and this evidence for engineering and low vision access review. Keep public-release acceptance open for the specific human, hardware, Windows-feature and installer checks above. No Microsoft API can supply a guarantee against future platform change.
