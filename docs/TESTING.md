## Beta 19 regression checks

Run these checks against the complete packaged candidate. [Beta verification](BETA-VERIFICATION.md) records the passing beta 19 run and exact executable identity; this section describes the regression coverage to retain for subsequent builds.

- **Compact display:** verify a readable page heading and visible page area at200% in a short window. The routine save/privacy reminder stays out of the way; an actual save failure must remain visible and readable. Quick theme labels and UIA status must update in both directions while keeping text size and independent preferences.
- **Single-input stability:** use Control, Mapping and Hardware with standard Xbox, Adaptive front and Adaptive ports layouts. Cover the CVI preset, independent one-input mode, Minimal and ordinary presentation at desktop 100% and small-window 200%. Check that changing and unchanged activity polls, held A on Next/Previous/Inspect and disconnect/reconnect keep the chosen input and actual focused button stable. The full drawing and duplicate lists must stay hidden in single-input mode. Check visible and accessible **Input n of total** feedback. Isolated report: `simple-controls-stability.txt`.
- **Profile selection:** the header's **Profile** button opens an owned choice window. Explore without activating, explicitly select with A/Enter/click, cancel without changing the profile and restore focus to the source button. In **Profiles**, ordinary row buttons must retain the active profile while focus moves; only an explicit activation applies another profile. Check current-profile name/status and neutral rearming after a switch. Isolated report: `profile-selection-access.txt`.
- **Shortcut recording:** route the temporary A select/B next/X previous/Y cancel layout through the real owned recorder controls. A on the recorder must not capture Enter; Y must cancel without capturing Escape. A physical keyboard records the actual shortcut, including Tab or Escape, then focuses **Use shortcut**. Check controller-only cancellation, accepting a physical Ctrl+K recording, restoring the prior layout and pause state, and neutral after closing. No synthetic desktop input should be emitted. Isolated reports: `shortcut-tab-capture.txt` and `shortcut-switch-navigation.txt`.
- **Pause and recovery:** pausing must release and stop mapped desktop output while allowing navigation only within Relay's registered configuration windows. With the fixed four-switch layout, reach and invoke **Resume control** through the actual WPF controls. Repeat through an owned choice window and shortcut recorder. Changing the foreground to another application, a native file dialog or Relay's typing keyboard must not permit paused controller navigation or typing. Check held-edge suppression and release-to-neutral boundaries. Isolated report: `paused-controller-navigation.txt`.
- **Advanced native choices:** under the fixed four-switch layout, A opens the actual dropdown, B/X highlights without changing the saved value, A applies once and Y cancels. Check every option, both endpoints, real settings/description handlers and restored source focus at 100% and 200%. Physical Tab and standard-controller RB must retain ordinary field traversal. Isolated report: `native-popup-switches.txt`.

These fixtures use actual WPF controls with synthetic controller input and recorded output. They do not establish physical-switch comfort, spoken Narrator output, native typing or live Windows-dialog acceptance.

## Native pointer and keyboard checks

These optional integration modes intentionally move/click/type through the real controller processor and Windows input sink. They use isolated test windows and temporary preview profiles; they do not start normal controller polling or save user profiles/settings.

| Mode | What it checks | Passing evidence |
| --- | --- | --- |
| `--pointer-test <absolute-output-folder>` | Native controller pointer movement into the page list, page clicks, continued movement across all ten pages, stick/D-pad coexistence and recovery after simulated unmarked mouse movement | `pointer-sidebar-input.txt` |
| `--keyboard-test <absolute-output-folder>` | Controller click on Relay's keyboard, native text in an owned editor, Shift, Ctrl+A, Backspace, retained editor focus and input cleanup | `keyboard-input.txt` |
| `--input-test <absolute-output-folder>` | Pointer test followed by keyboard test | Both reports above |

When Windows refuses automatic activation, append `--wait-for-test-focus`. This waits up to three minutes per activation stage for the user to bring the actual owned test window forward. It keeps every foreground/window guard in place.

1. Run the desired mode from an interactive desktop. For example, `XboxControllerMouse.exe --input-test D:\RelayChecks\input --wait-for-test-focus`.
2. For the pointer stage, activate the visible Relay verification window, using Alt+Tab or its title bar. Let the test move through its pages without switching to another app or holding a mouse button.
3. For the keyboard stage, activate the window titled **Relay keyboard input verification**. Let its keyboard/editor sequence finish. In the combined mode this is a second activation stage.
4. Inspect the report files and process exit result. A `failure.txt` that says focus was refused before input is inconclusive, not a pass. A later guard failure also requires investigation; do not remove the guard or type into another app to force a result.

Windows restricts foreground activation and can refuse it even when documented eligibility conditions appear to be met. See Microsoft's [SetForegroundWindow documentation](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setforegroundwindow). User activation is the intended fallback here; there is no foreground-policy bypass. Once input begins, moving focus away aborts the fixture rather than reactivating Relay over another app.

Native input reports still use synthetic gamepad states and a simulated unmarked mouse message. They do not establish physical Xbox/Adaptive switch use, real mouse hardware behavior, live Narrator speech or braille acceptance. Historical beta 14 source attempts stopped at the foreground guard before input; record a new passing report for the exact current candidate before claiming native integration success.

Build with `.\scripts\Build.ps1 -Installer`, then run `.\scripts\Test-Installer.ps1`. The installer test refuses to run when an existing installation, startup entry, or shortcut is present. It installs into a workspace test directory, verifies registration and shortcut target, runs the installed app smoke test, reinstalls, and uninstalls its test copy. Never delete the guard to overwrite someone's installation.

When the prior installer is available, run `.\scripts\Test-Installer.ps1 -PreviousVersion 1.2.0` to verify an actual version upgrade before the installed-app and reinstall checks.

The scroll/haptics regressions cover fine-unit latency, polling-rate consistency, reversal, neutral reset, hysteresis, step repeat, axis preference, modifier behavior, stabilization, settings migration, accepted-input callbacks, hover dwell, observed boundaries, pattern expiry, cooldown, failed motor stops, and reconnect. The WPF smoke test also verifies real control hover and ScrollPattern 0%/100% readings in its own scrollable page.

## Remaining acceptance checks

The 1.4 profile/mapping regressions exercise every control's custom keyboard and disabled mappings, shared mouse ownership, trigger mouse hysteresis, settings-change release and rearming, remapped pause-chord suppression, relocated pointer/scroll modifiers, legacy tool migration, custom-key partial delivery cleanup, profile isolation/persistence, export/import, corrupt-library recovery, invalid imports and duplicate identities. The WPF smoke test also drives the actual mapping, copy, rename, profile-switch and reset controls without persisting user settings.

- Run the scenarios in `docs/BETA.md` with a physical controller. Exercise the shortcut recorder with Tab, Escape, modifiers and a screen reader; Windows may intercept global combinations.
- Check Mapping at 960×700, both themes and high contrast; scroll to profile controls and expand the mapping summary.

- Use a physical controller over USB and Bluetooth: precision, diagonal motion, double-clicks, drag/drop, scroll, triggers, and vibration. Detection alone is not interaction testing.
- Tune stabilization with intended users. Compare comfort, response delay, fatigue, accidental press rejection, and the ability to stop and reverse. Test each setting independently and in combination.
- Try target assist in browsers and several native apps. Check visible suggestions, nearby competing controls, moving away, drag suppression, slow UIA providers, changing windows, and local learning/forget behavior.
- Verify every available Windows tool shortcut and settings link. Test tool remapping, Sticky/Filter Keys coexistence, Narrator, OSK, voice features, and required hardware where available.
- Disconnect or pause during dragging, reconnect with controls held, and lock/unlock or suspend/resume. No held input should remain. While paused, navigate Relay with four switches and select **Resume control** without a mouse; controller typing and controller navigation in Windows file dialogs must remain stopped.
- Test four XInput slots, battery states, multiple controllers, tray startup, single-instance reopening, sign-out, shortcut conflicts, and read-only/corrupt storage.
- Check keyboard and screen-reader navigation, contrast modes, animation disabled, 100%/150%/200% scaling, and mixed-DPI monitors. Automated contrast renders check the app palette, not an end-to-end Narrator or Windows contrast-mode session.
- With live Narrator, verify sidebar Right → heading → Down → first control, readable Up/Down order, real neighbouring panes and LB/RB through expanded sections/header actions. Check sliders/text fields retain their arrows and B returns correctly from controls, popups and dialogs.
- In single-input mode, keep Next or Previous focused while using other inputs and let unchanged activity polls continue. Confirm stable selection, position feedback, no reappearing diagram/list, no repeated speech and no lost focus. Repeat with Adaptive front/ports layouts and named remapped accessories.
- Explore the header profile choices and the saved profile buttons with Narrator. Focus alone must not change the active profile; A/Enter/click must apply the named setup. Cancel must retain the current controls.
- Open **Record keyboard shortcut** with a controller, cancel using only A/B/X/Y, then record a real keyboard shortcut and choose **Use shortcut**. Repeat while desktop output is paused. Controller Select/Back must not record synthetic Enter/Escape, and closing must restore the original layout and pause state.
- In **Accessibility → Display and reading**, verify each setting button speaks its name and saved value. Open a choice, explore all options without applying them, then select with A/Enter or cancel with B/Escape/Cancel. Confirm speech for the current-choice marker and restored source-button focus at large text sizes. Repeat with **More display options**, **Controller feedback** and the **Choose an input** button in Simple view. Try pointer reading inside the choice window without moving keyboard focus or changing the saved value.
- With **Accessibility → Read items under the pointer** enabled, rest over controls and plain text. Confirm useful speech after the pause, no focus/activation change, cancelled stale reading and no unchanged-text repetition. Turn Relay's option off if native Narrator mouse reading duplicates it; test both scan modes and the tester's braille display separately.
- Install/upgrade/uninstall on clean supported Windows machines without .NET. Verify retention of existing v1 settings and learned choices, startup opt-in, and removal of the Run entry at uninstall.
- Trusted code signing is required before broad distribution. The locally generated app and installer are unsigned.
