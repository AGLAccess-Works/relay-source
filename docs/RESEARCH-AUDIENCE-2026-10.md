# Relay: audience and accessibility research

12 October 2026. Assessment began with the beta 18 source and documentation, checked against current primary guidance. The beta 19 implementation outcomes are recorded in [Code review](DEEP-REVIEW-2026-10.md) and [Beta verification](BETA-VERIFICATION.md). The remaining recommendations and user journeys below are proposals; live audience acceptance has not been conducted.

Relay has a credible purpose: letting someone operate everyday Windows tasks through a controller, including adaptive switches and joysticks. Its strongest direction is predictable digital navigation, readable settings, a short setup, and truthful descriptions of what the hardware can report. The next priority is reliable selection and focus in the single-input view, followed by testing complete tasks with people using their actual access methods. More settings or a further whole-app redesign would not establish audience fit.

## What the current project supports

The local review covered [README](../README.md), [Guided setup](GUIDED-SETUP.md), [Visual Access](VISUAL-ACCESS.md), [Narrator](NARRATOR.md), [Controller identity](CONTROLLER-IDENTITY.md), [Recorded verification](BETA-VERIFICATION.md), and the main window, visual preference, presentation and single-input source files.

The documented beta already provides four setup steps; independent reading and physical-support choices; fixed A/B/X/Y navigation for four-switch layouts; large text, spacing and theme controls; an optional single-input presentation; keyboard/controller traversal; UI Automation names and action patterns; and a keyboard that supports the fixed switch layout. Keeping these together addresses overlapping access needs better than separating people into a visual-disability profile or a physical-disability profile.

Recorded automated results are useful regression evidence. The same documentation explicitly leaves live Narrator/NVDA, physical switches, braille, mixed-DPI and installation acceptance outstanding. This assessment did not conduct those live tests or recruit users. A claim that Relay works flawlessly for the entire target audience is therefore not supported.

| Intended user or task | Existing strength | Remaining audience risk |
| --- | --- | --- |
| Blind person using Narrator and a controller | Named controls, digital navigation, heading and pane traversal | Actual spoken output, interruption, repeated announcements and recovery need listening tests |
| Low-vision person using large text or Magnifier | Saved text/spacing/contrast choices and reflow | System scaling plus Magnifier can differ from Relay-only text scaling; focus must stay visible |
| Person using four accessible switches | Fixed next/previous/select/back and keyboard key traversal | Many sequential presses may cause fatigue; real switch bounce and motor timing remain untested |
| Person using a joystick and click switch | Joystick profile, fine pointer movement and assistance | Comfort, usable dead zones and safe transitions to menu navigation need physical testing |
| Person with CVI or difficulty with visual complexity | Optional single-input view and separate visual preferences | One preset cannot suit every person; selection changes must not introduce layout movement or competing feedback |
| Person with both visual and physical access needs | Reading and physical choices can be combined | The complete setup-to-typing journey must work without a sighted helper or an unavailable stick/button |
| Person who can use only one switch | No automatic scanning is documented | This user is outside the current standalone interaction coverage; four switches must not be described as universal switch access |

Microsoft's input guidance explains why remapping alone does not remove barriers: analog-only interaction, simultaneous combinations, repeated presses and sustained holds can still exclude users. Its adaptive-controller product page describes a configurable hub for external devices, rather than one uniform accessory layout. Relay should retain explicit input requirements and show each user's assignments. Applying gaming guidance to a Windows utility is a design inference, not a claim that Relay is a game or conforms to a certification scheme. [Xbox input guidance](https://learn.microsoft.com/en-us/xbox/accessibility/xbox-accessibility-guidelines/107), [Xbox Adaptive Controller](https://www.xbox.com/en-US/accessories/controllers/xbox-adaptive-controller/)

## Research-backed design direction

**Keep the user's neutral design direction and make its interaction states unmistakable.** A quiet rail, restrained controller picture, readable inspector and outlined controls can reduce competition for attention. Keyboard focus, the input being inspected and a physical input currently pressed need separate meanings. Focus must remain visible even when the page scrolls, scales or opens a dialog. Microsoft specifically calls for clear focus on every interactive element and prevents focus from disappearing into hidden or off-screen UI. [Xbox focus guidance](https://learn.microsoft.com/en-us/xbox/accessibility/xbox-accessibility-guidelines/113)

**Make single-input mode an optional presentation with independent adjustments.** Perkins describes visual clutter, closely grouped objects and unpredictable arrangements as access barriers for people with CVI. It also stresses individual differences, autonomy and choice. The implication for Relay is to let users choose the amount shown, size, spacing, colour and motion separately. Do not market one black background, one colour, larger text or a single-input card as a treatment or as suitable for every person with CVI. [Perkins: impact of clutter](https://www.perkins.org/cvi-impact-of-clutter/), [Perkins: CVI and individual access](https://www.perkins.org/cvi-awareness/)

**Keep controls stable and instructions short.** W3C's cognitive-accessibility guidance recommends consistent visual design, clear controls, understandable steps and concise text. Its step guidance includes current progress and important choices. For Relay, retain four short steps, show the current step and a brief choices summary, and use the same action wording across pages. Put optional explanations within reach, but do not hide essential decisions in expanded sections. These web guidance patterns are useful design references for a native desktop application; they do not themselves establish desktop standards conformance. [W3C cognitive usability guidance](https://www.w3.org/TR/coga-usable/#make-each-step-clear-pattern)

**Preserve native semantics rather than relying on the picture.** Windows guidance prioritises keyboard access, accessible names, customization and UI Automation. A controller graphic can help someone recognise their hardware, while named buttons and a text alternative keep the task available without visual recognition. Custom controls must expose their actual role, value/state and action, and should be checked with the real screen readers used by the audience. [Microsoft Windows accessibility overview](https://learn.microsoft.com/en-us/windows/apps/design/accessibility/accessibility-overview)

**Give useful feedback without creating a speech queue.** Xbox narration guidance covers names, roles, values, context changes and action confirmation, while cautioning against repeated instructions. In Relay, an input-selection announcement should describe the selected input and its assignment once. Ordinary polling, a held physical button or unrelated stick movement should not continually repeat the card or interrupt the next item. Hover reading must remain opt-out and must not activate a control or move focus. [Xbox narration guidance](https://learn.microsoft.com/en-us/xbox/accessibility/xbox-accessibility-guidelines/106)

## Highest-value polish changes

The following order is an engineering and product recommendation inferred from the user report, source review and guidance above.

1. **Fix single-input selection before visual additions.** During this audit, the implementation investigation confirmed a defect: a cached presentation refresh showed the ordinary input tiles again while the single-input view was enabled. This is a software defect, not a user difficulty. The card, inspector, picker and mapping editor must agree on one selected input. Next/Previous changes it once; pressing a physical controller input changes its activity state without selecting a different card. Keep the actual focused button and its scroll position through refreshes. Add a visible and accessible position such as “Input 3 of 16” where the actual list supports it. Record the fix and its focused regression separately from the research recommendations.
2. **Keep single-input mode visibly quiet.** Hide the whole-controller picture and tile strip in that mode, keep the selected input and its action in fixed locations, and avoid duplicated always-visible detail or activity panels. Keep Change assignment, Back and access to display preferences reachable. Do not add extra motion as a selected-state cue.
3. **Use one home for appearance preferences.** The existing direct choice rows fit the reference well. Settings still exposes an additional appearance checkbox and size dropdown, while Accessibility contains the direct choices. A simple route to the same named Display and reading section would reduce competing mental models. Preserve the header's quick theme action and all saved values.
4. **Make the current control layout available at the point of use.** Show a compact, optional “Your controls” summary generated from the actual profile. Avoid assuming B means Back: in the four-switch layout B means Next and Y means Back. A persistent summary can reduce memory demand without repeatedly reading the entire guide.
5. **Use task wording and explain consequences.** Prefer “Choose an input”, “Change assignment”, “Unassigned” and “Saved accessory” consistently. An action labelled “Use dark theme” or “Use light theme” describes the result more clearly than “Light / dark”. Avoid unexplained CVI terminology as the only label; “One input at a time” describes the behaviour. Separate choosing an input from trying its assigned Windows action. Keep a mapping change confirmable and recoverable.
6. **Refine contrast and hierarchy without adding boxes.** Use a clear primary heading, one useful instruction, then the next action. Keep contrast checks on resolved text and meaningful state/focus edges in every supported theme. Use 4.5:1 for normal text and 3:1 for meaningful control/state indicators as evaluation benchmarks, including dark mode and Windows contrast colours. These are benchmarks for review, not a claim of WCAG conformance. Thin strokes can remain harder to perceive despite a nominal passing colour ratio. [W3C text contrast](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html), [W3C non-text contrast](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)

No automatic accessory-presence claim should be added to polish the ports view. The existing identity guide distinguishes a user-recorded physical socket from the logical Xbox input received. Keep that distinction visible when several accessories or remapped sockets can produce the same logical input.

## Acceptance scenarios for audience fit

These are proposed tasks, not completed results. Run them on the shipped candidate, record assistive-technology/Windows versions and actual input hardware, and ask the person to use their usual preferences. Measure task completion, unexpected activations, recovery, confusing labels, required help and physical effort. Do not impose a fast completion target on switch users.

| Scenario | Passing result |
| --- | --- |
| First launch with Narrator already running, four switches and no mouse/stick | Person completes all four steps, combines reading and physical help, saves, then understands their resulting controls |
| Single-input mode: select every standard input with Next and Previous | Selection moves once per press; card, inspector and assignment stay in agreement; focused navigation control remains visible |
| Single-input mode with Adaptive front and ports views, named accessories and different logical remaps | Current item is valid in each view; friendly name and actual logical input are distinguishable; activity never claims a physical cable is connected |
| Keep Next focused while holding or releasing another input and moving a stick | No jumping, lost focus, unsolicited selection, duplicate activation or repeated selection announcement |
| Select the first/last input and change window size, text size, page and presentation mode | Boundaries are understandable; selection recovers deliberately if unavailable; focus lands on a visible appropriate control |
| Narrator-only mapping and profile tasks | Person can inspect an input, change its action, identify a saved/current profile, cancel and return without sighted assistance |
| Four-switch typing into an ordinary editor | Person opens the keyboard, enters and corrects text, uses Space/Shift/symbols and hides the keyboard while the editor remains the typing target |
| BLV and physical needs together, 200% Relay text, actual Windows scaling and Magnifier | Essential actions remain readable/reachable; no clipped or obscured focus; navigation order matches the presented order |
| Pause, reconnect, profile change and held controls | No queued unwanted click/typing; status is understandable; user can recover through their available inputs |
| Save failure, cancelled setup and accidental mapping change | Clear understandable feedback, no silent loss of the prior usable setup, and a reachable recovery path |

Microsoft recommends pairing automated checks with manual assistive-technology tests and specifically testing main scenarios by listening to Narrator, including completing them without looking at the display. A passing UI Automation inventory does not substitute for these journeys. [Microsoft accessibility testing](https://learn.microsoft.com/en-us/windows/apps/design/accessibility/accessibility-testing)

For a targeted beta, recruit people across the actual supported combinations: blind screen-reader users; low-vision magnification users; physical-access users with switches and joysticks; people with CVI who want to try the optional view; and people with combined needs. Let a supporter participate where that reflects normal use, while distinguishing independent setup from supported setup. Record disagreements about the design rather than treating them as failures by the user. Research can guide the next iteration; successful use by these people is the evidence that Relay is reaching its audience.
